# 固定依赖镜像与运维交接

记录日期：2026-10-20（Asia/Shanghai）。用户确认：依赖已由同事预装到固定基础镜像，常规代码发布约2–3分钟；发布时不能假定依赖会随源码动态更新。本文是后续开发、审计和发布的交接规则，不是镜像构建脚本。

## 依赖入口及影响范围

| 入口 | 内容 | 交接重点 |
| --- | --- | --- |
| `requirements.txt` | API、Gateway、MCP等运行依赖及extras | 包增删、版本/范围、来源变化；运行基础镜像 |
| `scripts/sandbox_venv/requirements.txt` | 独立沙箱解释器的库 | 沙箱环境需单独更新和核验，不能只检查宿主环境 |
| `requirements-dev.txt` | 测试工具 | 默认仅影响开发/CI；如相关镜像预装这些包也需同步 |
| 内部DeepCube wheel | 非公共PyPI包，环境相关制品 | 包版本、制品名、SHA256、Python ABI/架构及目标环境，不能只看相同文件名 |
| Python、系统库/可执行文件 | Python版本、FFmpeg等原生依赖与系统环境 | 基础镜像、OS/架构、共享库及wheel兼容性 |
| `console/vendor/`等随源码分发的第三方资源 | 前端第三方静态库 | 记录版本、许可证及缓存引用变化；通常随代码发布，不要求重建Python依赖镜像 |
| 新增第三方import、改用库的新API或可选extras | 可能未体现为requirements改动的运行要求 | 核对固定镜像是否包含及最低版本，不能用本机可运行代替 |

以上清单是依赖声明入口，不是生产镜像的完整冻结清单。版本范围和间接依赖可能在重建时重新解析；无需求不要顺手放宽固定版本或批量升级依赖。

## 每次开发和发布的规则

1. 相对上次已发布/指定基线检查上述入口及新引入的运行要求，标明比较基线。只有注释变化时说明“声明注释调整，依赖集合/约束不变”。
2. 有调整，在CHANGELOG或发布记录及最终交付中单列“依赖变更（运维）”，供用户直接转发；不替用户向运维发送消息。
3. 将代码交付与镜像更新要求写清。需新包/版本/原生环境时，声明本版本须搭配更新后的镜像；不能只改requirements后就称普通代码发布会生效，也不在启动时自动pip安装来规避。
4. 验证区分本地、CI和目标镜像。目标镜像尚未验证时如实标记；本机pip freeze不能当作生产镜像事实。
5. 无调整也写“依赖变更：无（相对……）”。这不等于宣称线上镜像已核验，不要求纯代码发布重建镜像。

本轮建立规则时，`v0.13.9`相对`v0.13.8`未调整上述依赖入口，也未引入新的第三方库；只是新增可选会话标题参数。没有安装或升级任何依赖。

## 可直接转发的汇总格式

```text
依赖变更（运维）
代码版本/提交：
比较基线：

包或系统组件 | 变更类型 | 旧版本/范围 → 新版本/范围 | 影响环境
……

原因与兼容约束：
验证结果：本地 / CI / 目标镜像（未验证则明说）
需重建或更新：运行基础镜像 / 沙箱环境 / CI镜像 / 无
代码与镜像配套要求：
回退配套：代码版本 + 原镜像tag/digest
```

不得包含Token、私有仓库密码、签名下载地址或其他凭据。内部制品使用可识别的名称、版本和哈希交接。

## 镜像基线由运维提供

实际基础镜像名称、不可变digest、构建日期、Python/系统版本、宿主与沙箱的完整安装清单、内部wheel版本/哈希应随镜像交接保存。目前这些实物信息尚未在本仓库核实，不填入推测值。镜像重建时需关注间接依赖解析差异，并验证导入、联合健康、沙箱及受影响能力。

仓库`deploy/jenkins/Jenkinsfile.gateway`与`Jenkinsfile.api-only`当前仍含apt/pip安装步骤，是现存源码示例；同事最新简化流水线可能在实际Jenkins Job或其他构建仓中。本文不改这两份脚本，不假装它们已经与当前运维流程一致。
