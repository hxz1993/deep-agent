# 30 · UI 工具同 Run 等待与执行连续性

> 首次研究：2026-09-26。状态：设计课题，尚未实施；本次仅更新文档。
> 核验基线：DeepAgent v0.11.5；Pydantic AI 2.46.0、Harness 0.32.0、Monty 0.0.23；数据库 Head 007。

## 目标与当前决定

保留现有 UI 工具的业务定义和渲染格式，研究将“工具发出后结束 Run、用户回答后新建 Run”改为“原 Run 有界等待答案后继续”。主要收益是保留文件缓存、PTC REPL、文件载荷引用、Planning 和运行状态，减少跨 Run 恢复逻辑。

- 优先使用 Core `HandleDeferredToolCalls` 接住现有 ExternalToolset 请求，不切换到 Harness AskUser 的固定选择题 Schema，不重写 SDK。
- 等待需要超时、取消和资源清理。五分钟是讨论中的候选值，尚未定稿，不因此预埋环境变量。
- 用户接受断开或超时后结束当前执行，之后重新提问；长期等待、服务重启恢复活跃协程不是目标。
- 用户倾向降低复杂度，可以考虑服务端与电子表格等客户端协调升级。**能力协商、双模式不是已确认方案**，不默认实现版本号矩阵。
- Choices 已归档为潜力、当前不接。MCP 参数校验和用户答案候选值的额外后端兜底校验，不随本课题实施；已有鉴权、调用归属与幂等保护仍需保留。
- 不承诺解决所有重复澄清或计划重写；真实模型对照尚未完成。

研发状态只在 [TODO](../TODO.md) 维护。工具定义的当前说明见 [01 UI 工具](../01-ui-tools/README.md)，当前已发布通信契约见 [UI 工具协议](../../guides/ui-tools-external.md) 和 [SSE 协议](../../guides/sse-protocol.md)。本稿不表示线上协议已经改变。

## 为什么重新评估

之前已有三处记录：

- [05 工具优化 §8](../05-tool-optimization/tool-optimization-design.md)：`HandleDeferredToolCalls` 被列为通用 Deferred 处理，原建议为“不替换现有产品化 HITL”。
- [2026-09-22 Core 升级评估](../../../../agent-labs/upstream-agent-references/indexes/deepagent-core-assessment-20260922.md)：旧评估记载 v2.35.0 已有此能力，指出它没有替我们提供跨 HTTP 持久化、权限和幂等协议。因此不能将其描述为本次升级才出现的新机制。
- [15 浏览器与页面操作：即时动作与人工交互分流](../15-browser-and-page-actions/browser-and-page-actions-design.md)：明确建议即时页面动作通过 Future 在同 Run 内等待，人工选择／确认则用 Deferred 跨 Run，以避免用户久等或刷新时长期占用执行资源。旧方案并非不知道同 Run 等待可行；工具优化中的相关记录可追溯到 2026-07-29 提交 `3a03685`。

旧判断一方面关注“能否直接替换整个产品交互链路”，另一方面优先释放资源与支持跨请求恢复，并将同 Run 收益主要视为少一次请求。现有记录没有完整比较 PTC REPL、文件缓存、Planning 恢复与客户端改造成本。不能把“官方不负责持久化／权限／幂等”直接推导成“同 Run 等待不值得采用”，也不能把“人工交互必须跨 Run”当成框架限制。

本次用户明确接受有界等待、断开／超时后重新提问，且已验证 PTC 内存断点，因此重新权衡。保留原 UI 定义，调整运行生命周期；仍需我们实现答案接收、事件落库、生命周期与客户端适配。当前是有验证依据的候选设计，并未证明所有场景下优于旧方案；不据此倒推当时所有讨论或原始需求。

## 已核验的状态差异

| 状态 | 当前 Deferred 跨 Run | 同 Run 等待 |
| --- | --- | --- |
| PTC/Monty REPL | 新 Run 新建 REPL，变量与中间对象不恢复 | 继续使用原 REPL；显式 restart、运行失败等仍可能重置 |
| 文件字节／解析缓存 | 新 AgentDeps 新建缓存，再读可能重新下载或解析 | 复用同 Run 缓存 |
| PTC 文件载荷引用 | 不透明引用绑定原 Run，新 Run 不接受旧内存引用 | 等待前后仍在原授权运行范围内 |
| Planning | 根据同 Turn 的已存快照新建并恢复 PlanStore | 保留原 Store，无需等待前后恢复 |
| 已披露工具 | SDK 从可见历史中的 ToolSearch 证据恢复；并非必须重搜全部工具 | 延续当前运行，仍按每步工具准备规则执行 |
| 已加载 Skill | SDK 根据历史恢复已加载能力；运行实例和产品遥测重建 | 原运行生命周期继续 |
| 请求次数预算 | 本项目从同 Turn 的事件恢复累计次数 | 延续当前计数；不能把等待当作预算重置 |
| 上下文运行态 | 重建临时估算、样本和遥测；已存历史／压缩结果不丢失 | 保留内存状态，但不跳过后续正常压缩 |
| MCP 连接 | Run 退出关闭，下一 Run 调用时按需重连 | 可复用连接；远端空闲超时仍需处理，写操作不能盲目重试 |

同 Run 是框架状态连续，不代表模型在供应商侧一直思考，也不保证不再发送历史或工具 Schema、不再产生输入 Token。

Planning 当前另有恢复边界：`latest_plan_snapshot` 仅扫描同 Turn 最近 20 条 `tool/results`。快照在窗口外时可能恢复为空；这是源码发现，尚未证明是用户所见计划重写的根因。如果保留跨 Run 恢复入口，不能因新增同 Run 路径而忽视该问题。

## 隔离验证依据

2026-09-26 使用本机 SDK 与产品 `HybridCodeMode`，以 FunctionModel 固定调用序列，不访问真实模型、业务数据或 8000 服务：

```text
run_code: value = 41
→ 自定义 ExternalToolset UI 工具，参数仍为 fields，结果仍为 confirmed + values
→ run_code: value + 1
```

- 加 `HandleDeferredToolCalls`：只有一个 Run，第二次代码返回 42。
- 默认 Deferred、带结果重新启动：产生两个 Run，第二次代码提示 value 未定义。
- 另用异步 Future 验证等待期间任务未结束；回答前后 run_id 与依赖对象一致。
- 工具披露恢复 15 项、Planning 7 项、PTC Run 隔离 1 项现有测试通过。这些不等于全产品同 Run 接入完成，也未验证真实模型重复提问、浏览器断开、长时间等待或客户端兼容。

当前验证是“PTC → 原生 UI 工具 → PTC”。本课题不顺带开放 PTC 脚本内部调用 UI 工具。

## 目标链路

```text
聊天请求建立 SSE，启动 Run A
→ 模型调用现有 UI 工具
→ 原有参数校验通过
→ 官方 handler 接住 Deferred 请求
→ 注册待答交互，确认问题事件持久化，发布待答状态／工具调用
→ Run A await 答案，保持内存和心跳
→ 客户端通过答案提交请求回传现有业务结果
→ 后端核验身份、交互归属与是否仍可提交，将结果交给等待者
→ 原工具结果进入同 Run 的 SDK／Event／SSE 链路
→ Run A 继续，最终完成或取消并释放资源
```

handler 仅处理本课题支持的 UI 交互，不自动批准其他审批请求。未处理的工具如何拒绝或沿旧路径交出，随部署兼容决策确定。

### 持久化与锁

当前 Runner 会缓存 UI 调用，待 Run 返回并确认持久化后才向客户端发布。目标是在 handler 等待前确认调用已落库并发布，不能等 Run 完成，否则用户看不到问题、后端拿不到答案。

继续使用 `chat_sessions + chat_session_events` 作为事实源，不另建会话历史。待答登记必须先于可操作事件发布；发布失败或持久化失败时取消登记。工具结果只由一条路径写入，避免答案 API 与 Runner 重复落库。

当前 Run 持有会话执行锁。答案接收路径不得再次等待同一执行锁，否则会死锁；也不得按普通聊天入口创建第二个 Run。等待时阻止并行新聊天，明确让用户先回答或停止。

拟复用现有 Event payload／metadata 表达等待与终态，暂不计划新增配置表或安装字段；是否需新增运行状态枚举或数据库迁移，实施前核对事件、序列化和投影后再定，不将“没有 DDL”当成已验证结论。

### HTTP／SSE 与客户端

保留现有工具名称、参数 args、结果 result、widget 和工具提示。新增的交互定位信息属于传输层，不塞进每个助手的业务 Schema。

拟使用服务端交互标识关联等待者，并绑定用户、Agent、Session、Run、具体工具调用事实。不能只依赖 tool_call_id 全局唯一：同 Run 不同步骤也可能复用它。端点与事件名尚未定稿。

SSE 需要表达“等待用户”和“恢复执行”的非终态；只有完成、失败、取消、超时才关闭该次执行。待答期间保持心跳，核对代理空闲／总时长限制。答案请求返回接收结果，模型后续输出继续走原执行流；ACK 丢失后的重提需要幂等，不能重复推进工具。

Console 当前在 streaming 时拒绝提交，并在恢复时清理计划后发起新 chat；必须适配等待状态、答案提交、计划保留与终态。电子表格和 DeepCube 客户端需做同类适配；表单字段可不变，但不能声称客户端零改动。只读轨迹观察流不具备答题权限，关闭观察流不取消生产者。

## 超时、断开与资源回收

建议首版采用请求持有 Run：生产者 SSE 断开被服务端检测后取消，不要求客户端用 unload/beforeunload 上报关闭。关闭页面、刷新、断网无法可靠区分，断开检测也不保证立即发生；独立等待上限兜底。

超时或取消结束当前 Run，保留会话历史，关闭旧交互；不把超时当成用户同意，不自动代选继续执行。用户回来后可重新提问。服务进程退出不恢复内存等待者；历史遗留等待必须表现为不可继续提交，不能假装仍有活跃 Run。

回答、停止、断开、超时只允许一个结果取得交互终结权，迟到或重复答案不得启动模型第二次执行。结束时释放等待任务、Future、MCP 连接、PTC REPL、缓存与活动执行登记。

五分钟候选仅指一次等待用户的窗口，不直接作为所有模型／工具执行的总时限。等待时间、执行时间在诊断中可区分，Usage 仍来自真实模型响应；不得为了等待重置请求预算。

同 Run 保留内存也会保留大文件和 REPL 资源；需检查现有并发限制及沙盒／网关超时的交互。多 worker 时答案可能路由到另一进程，实施前明确同进程路由或协调方案，不能静默假定生产单 worker，也不在本稿默认引入分布式等待平台。

## 借鉴 AskUser 的范围

保留自身 UI 业务格式，只借鉴适用的指导和状态设计：

- 仅询问上下文和可用工具仍无法确定、且影响下一步的信息；不重复询问已提供内容。
- 独立问题尽量合并一次问；存在依赖的问题分步问。现有多字段、答案映射、推荐理由与自由输入是已有能力，不另建一套。
- 问题描述具体，选择含义清楚；业务候选来自真实工具／上下文，不编造。
- 取消、跳过、超时与正常回答分开。用户拒答后不立即机械重复；可独立进行的部分继续，需要明确确认的写入不能擅自代选。
- 待答、已答、取消／过期等状态清晰，问题与回答可关联到轨迹；沿用现有身份隔离和调用归属。

不照搬官方单选／多选限制，不删除自由输入、搜索、分页或业务编码；不引入本轮用户已否定的额外答案枚举兜底校验。原有模型生成工具参数的 Schema 校验保持。

## 兼容策略：待决

| 选项 | 适用条件与成本 |
| --- | --- |
| 协调升级，目标只维护同 Run 模式 | 用户当前倾向降低长期复杂度；需列清服务端、Console、电子表格／DeepCube发布依赖，切换时完成正在等待的旧交互或明确终止，旧客户端不能误触发新协议 |
| 客户端能力协商，暂保留旧模式 | 无法协调发布时的备选；旧客户端跨 Run，新客户端同 Run，需要维护两条执行路径及验收矩阵，不默认采用 |

不能通过仅复用 run_id 或 AgentDeps 就宣称保持同一 SDK Run。历史 Turn/Run 仍按原事实读取；不删除 turn_id、改写既有轨迹。发布模式、旧 pending 数据处置、回滚时活跃交互清理需要一起决定。

## 验收范围与未决事项

实施验收至少覆盖：

1. 现有电子表格、DeepCube、内置选择／确认与有前端副作用的 UI 工具，原定义及结果结构可用；Agent 包原版导入、覆盖、再导出无结构变化。
2. `run_code → UI → run_code` 变量保留，文件只读／解析一次，文件载荷引用仍有效；Planning不清空；工具披露、Skill、预算和Usage连续。
3. 问题落库后及时展示，答案ACK与后续SSE正确；多个UI调用、部分回答、重复提交及复用tool_call_id不串答，不扩大工具授权。
4. 等待中停止、断开、超时、删除会话、服务退出、迟到答案均不产生第二次工具执行或悬挂资源；代理与worker路由按部署方案验证。
5. 历史重开、只读观察、轨迹、工具结果关联、标题、压缩、取消与诊断无回归；真实模型比较重复澄清／重写计划，不把SDK模拟结果当成真实效果证明。
6. 按最终兼容策略验证旧客户端或协调升级拒绝路径；回滚不会留下看似可操作的无主表单。

待决：发布是否协调升级；等待时限；生产者断开是否立即取消；多worker部署约束；协议字段／端点；历史pending和回滚处置。除课题建档外，未授权开展跨仓客户端修改或发布。
