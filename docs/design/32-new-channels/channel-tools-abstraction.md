# 通用渠道工具设计

> 2026-09-28。设计稿，尚未实现。先提供通用协议与飞书适配，企微继续使用已验收的收发逻辑。
> 当前基线：v0.11.9，test 分支提交 77a27a8，已推送，无 Tag。之前的飞书专用媒体工具已完整撤回。

## 目标与边界

让 Agent 通过一套稳定的渠道工具发送图片、文件与消息，查找获准联系的目标、读取获准访问的聊天消息。工具名、主要参数及授权语义不随渠道变化，平台差异由网关的适配器处理。先落地飞书，不等于为飞书另做专用工具。

普通答复继续用现有流式回复；图片和文件作为独立消息发送，可引用原消息或投递到指定话题。首版不做图片嵌入流式卡片，也不改飞书加载动画和企微回复效果。上传媒体是发送过程内部步骤，不额外要求 Agent 调上传工具、管理 image_key/file_key。

本文描述拟新增的能力，不代表当前发布版已恢复图片和文件发送工具。扫码、帮助界面、入站图片、流式回复和已有引用效果均保留。

## 上游依据与取舍

| **主题** | **OpenClaw** | **AstrBot** | **本项目方案** |
| --- | --- | --- | --- |
| 统一发送 | message 工具通过渠道动作适配器分发 | send_message_to_user 将有序组件转换为 MessageChain，再交给平台 | 一套 channel_message，适配器处理上传、格式和投递 |
| 消息操作 | 动作包括发送、表情、删除等，按插件能力开放 | 已核验的内置入口侧重组件发送 | 同一工具的不同 action，不为每个动作建工具 |
| 外部会话 | conversations_list/send/turn；区别于本地 sessions | 可指定统一会话标识；跨会话有管理员检查 | channel_targets 只发现授权候选，发送仍走消息工具 |
| 历史 | 平台消息读取与本地会话历史分开 | get_group_message_history 查本机持久化的当前群消息 | channel_history 明确读取平台消息；不复用 Agent Event Store 冒充 |
| 调度 | 触发和投递分层 | future_task 管理任务，再复用消息能力 | 本轮不新建调度工具；提供可被调度调用的发送服务 |
| 平台业务 | 飞书文档、日历、多维表格等由专门插件提供 | 平台业务可由插件扩展 | 不塞入通用渠道工具，继续由专用工具或 MCP 承接 |

OpenClaw 飞书官方插件本次核验实际声明 send/react/reactions/delete/unsend，不能把核心 message 动作全集当成飞书全支持。它还提供按当前渠道描述消息工具的机制；本项目借鉴能力裁剪，不照搬其所有动作和默认发送方式。

上游依据为 2026-09-27 至 28 日查询的官方 main/master 源码与文档，不代表用户安装版本。

## 三个工具

三个都是运行时内置系统工具，统一归入 `runtime:channel`，不是另起一个 MCP 服务。工具数量固定为三个，各次运行实际可见的工具和动作按权限、适配能力裁剪。

| **工具 / 展示名** | **首版飞书动作** | **覆盖场景** | **明确边界** |
| --- | --- | --- | --- |
| `channel_message` / 渠道消息 | send、react、reactions、delete、status | 发文字、图片、文件；引用回复；指定话题；获授权的主动投递；添加/取消/查看表情；撤回机器人自己发送的消息；查询操作回执 | delete 不能删他人消息；status 不是已读状态；不提供任意 SDK 方法透传 |
| `channel_targets` / 渠道目标 | list、resolve | 列出当前运行获准使用的用户/群/话题；按名称筛选；将候选解析为稳定目标引用 | 首版来源是已知渠道会话及显式授权目标，不默认遍历全企业通讯录；重名时返回候选，不能猜人 |
| `channel_history` / 渠道消息历史 | get、list | 读取引用的原消息、查看获准聊天的最近消息、按时间及游标翻页 | 平台来源；读单条、读聊天历史分别授权；不包含内部工具日志或模型思考；首版不提供全局全文搜索 |

`react` 通过 operation=add/remove 区分添加与取消。`status` 只查询本系统操作回执。编辑、置顶、投票、全局搜索、群管理作为后续适配动作，首版不暴露。语音和视频首版可按普通文件投递，不宣称支持语音气泡、视频播放器或语音识别。

三个工具共同覆盖“找目标 → 看相关消息 → 发送/操作”的流程。不再增加一个让模型反复询问权限的能力查询工具：可用能力、当前目标和必要限制直接放入可信运行上下文与工具说明。

## 公共参数与结果

### 目标、消息和内容

| **对象** | **关键字段与含义** |
| --- | --- |
| ChannelRunContext | 服务端持有 execution_principal、来源账号/发送人/聊天/消息/话题、grant 引用；不是模型可填写的参数 |
| ChannelTargetRef | 不透明 target_ref；服务端解析为账号、目标类型、平台 ID、可选话题。它只是引用，不是授权凭证 |
| ChannelMessageRef | message_ref；绑定账号、所属聊天、消息 ID、话题。删除、表情和读取都检查所属目标 |
| MessageContent | 有序 components：text(text)、image(file_id)、file(file_id, display_name?)；file_id 复用授权文件库 |
| ChannelOperation | operation_id、action、状态、每个组件的投递结果、message_ref、平台消息 ID、是否在当前聊天可见 |

默认 target 取可信当前聊天；非渠道运行必须指定已授权 target_ref。回复可使用 `reply_to="current"` 或经校验的 message_ref；`thread_ref` 必须属于同一目标。新增渠道只负责映射这些公共语义，工具不出现飞书专属字段。

示例：向当前聊天发送图片和附件，并引用本轮消息。

```json
{
  "action": "send",
  "reply_to": "current",
  "components": [
    {"type": "image", "file_id": "file_chart"},
    {"type": "file", "file_id": "file_report", "display_name": "月报.xlsx"}
  ]
}
```

一次调用可能创建多条平台消息，逐项返回结果，不假装是同一张卡片。组件按输入顺序投递；某项失败或结果未知，停止后续未发送项，返回已成功、失败和未发送项，防止标题与附件顺序错乱。

模型不传 App Secret、Token、平台上传 key、任意主机路径或下载 URL。图片生成/文件生成工具需要先将产物登记到文件库；URL 下载属于独立文件获取能力，不能绕过文件权限和下载校验。

## 除工具以外需要建设的适配

调用链：Agent 工具或后台触发 → ChannelOperationService → Gateway → 已注册的渠道操作适配器 → 官方 SDK/API。

| **层** | **新增职责与代码落点** |
| --- | --- |
| 工具装配 | 在 `api/v1/deps.py` 等运行装配入口接收可信渠道上下文；生成本次可见 schema；在 system_tools 目录登记中文名称、分组和轨迹展示 |
| 公共契约 | 在 `channels` 定义操作请求、能力声明、目标/消息引用、分页和统一错误；工具上层无平台分支 |
| 操作服务 | 授权、目标解析、文件权限、幂等、操作回执、顺序和取消；可由 Agent 或确定性的后台任务直接调用 |
| 注册表 | `channels/registry.py` 登记可选 ChannelOperationsAdapter 及 capability provider；现有入站/流式 ChannelAdapter 协议保持独立 |
| 网关 | 内部请求鉴权、运行授权复核、账号选择、连接代际、并发与生命周期管理；主动发送不依赖活动 MessageJob |
| 飞书适配 | file_id 内容转 SDK 上传；映射用户/群/话题和引用；调用发送/表情/撤回/读取接口；规范权限错误、限流、游标和实际消息回执 |
| 文件与记录 | 复用文件库；新增持久化操作和组件回执；平台消息引用与 Agent 轨迹关联，但不混淆两个历史来源 |

适配器声明动作、内容类型、引用/话题能力、大小/数量限制以及所需权限。模型可见能力是“已实现能力 ∩ 账号配置 ∩ 当前授权”的交集。平台权限能核验就预检，未知则标记未知；执行遇到权限不足要明确返回，不能把未知当成已授权。

源码核验：当前 lark-channel-sdk 1.4.0 提供公开 upload_media、send、reply、表情、撤回、fetch_message 等入口；平台聊天历史的私有 helper 忽略 before_id，且将错误吞成空列表，不能直接采用。历史列表改用官方 lark-oapi 公共接口，在适配器内处理真正分页和错误。对 Agent 来说仍然是相同的 channel_history。

飞书 worker 的 IPC 也需接入通用操作协议；账号重建后绑定新 generation，防止操作落到旧连接。企微暂不注册新操作适配器，无需给成熟回复接口补一批空方法。

## 加载时机与授权

| **运行入口** | **何时加载** | **默认权限范围** |
| --- | --- | --- |
| 飞书入站对话 | 创建 Run 时建立可信上下文，第一次模型调用前装配；不依赖本轮是否已有附件 | 当前聊天发送/引用；单条引用读取、表情等分别按动作策略开放；聊天历史列表需读权限 |
| 飞书对话需要联系其他人 | 当前运行具有管理员配置的跨目标授权时，增加目标发现及对应发送动作 | 只返回和访问授权目标；不是整个租户或渠道所有联系人 |
| 企微入站对话 | 首版不注入新工具；未来注册企微适配器后使用同一装配流程 | 保持当前已验收逻辑和已有 MCP 行为 |
| 普通控制台对话 | 默认不加载；Agent 及运行主体被明确授予渠道能力后才加载 | 由授权账号、目标、动作决定，不能仅凭 Agent 绑定渠道推导 |
| 定时、轮询、事件触发 | 若运行 Agent，启动该 Run 时根据后台执行身份装配；固定内容投递可直接调用服务，不需要模型工具 | 使用明确的执行身份和目标授权，不借用最近一位聊天用户 |
| 仅浏览历史 | 不创建 Run，不加载工具；恢复对话后的新 Run 重新计算 | 不沿用旧历史里的工具权限 |

运行时顺序：识别可信入口和主体 → 解析授权 → 获取适配器能力 → 裁剪工具及 action → 注入当前目标、引用和使用说明 → 模型调用 → 执行时再次校验 → 返回结构化结果。

新生成文件无需重开会话或重新注入工具。工具从运行开始就可见，file_id 在生成后取得。后续模型轮次重新检查权限与能力变化；不能原地改全局工具定义而影响其他会话。

**授权必须区别外部发送人和平台账号所有者。** 渠道会话记在某个平台用户名下，并不意味着渠道里的所有人都继承该用户的跨聊天权限。授权主体使用账号/租户/外部发送人以及来源群规则识别；当前回复由可信入站授予，跨目标、读历史、撤回等分别受控。

为跨目标运行设计 ChannelGrant：主体或主体范围、channel_account_id、目标范围、动作集合、有效期和撤销状态。首版提供管理员配置入口，默认只开当前会话；读取权限不从发送权限推导。模型正文、历史文本、target_ref 都不能创建或扩大 grant。

内部 Bearer Token 只证明请求来自服务，不证明某个目标已授权。内部调用携带服务端生成的 run/grant 引用，执行前再核查当前账号状态、主体、目标和动作。管理员禁用或撤销后，运行中已有工具也必须拒绝执行。临时断线返回可重试的不可用错误，不冒充“不支持此能力”。

## 投递可靠性与消息边界

- 持久化 operation_id，由服务端以 Run + tool_call + 组件序号生成稳定幂等键；后台触发使用任务执行 ID。相同键不同内容直接拒绝。
- 新增操作主表与组件结果表：保存主体/grant 引用、账号和 generation、action、目标、请求摘要、幂等键、状态、时间、file_id 引用、实际消息 ID 和脱敏错误。具体迁移号在实施时确定；当前版本不加表。
- 状态采用 accepted / running / succeeded / partial / failed / unknown / cancelled。每项分开记录上传和发送结果；成功意味着平台确认创建消息，不等于用户已读。
- 上传成功不等于发送成功。发送后落库前断线或进程退出会产生 unknown；有平台去重/核验能力时使用，没有则不盲目补发，也不承诺 exactly-once。status 查询不会触发重发。
- 部分失败后的重试保留成功项，不能整组重发。撤销只停止尚未派发项；已经发出的消息不会因取消 Run 自动消失。
- 账号停用、换密钥、worker 退出时，未派发操作终止，已派发未确认项记 unknown。操作服务纳入账号生命周期、超时和优雅停止，但不绑死在某次入站回复任务上。
- 操作回执本身也做主体/目标权限校验，不允许猜 operation_id 查看其他人的消息。

普通答案依然由原有流式路径发送；显式工具发送的内容返回 `visible_to_current_chat` 和逐项消息映射，提示模型避免再次粘贴。同一附件不会因为工具成功后又到最终回复阶段而自动重发。跨目标发送后，当前聊天可以报告结果；但不自动抄送目标聊天的全部内容。

现有 channel_message_runs 是入站处理记录，不能替代主动投递回执。现有 search_conversation_history/read_conversation_event 仍查 Agent Event Store；channel_history 返回 source=platform、消息时间、发言者、公开内容、资源引用与游标，不返回模型内部事件。平台内容一律作为不可信消息数据。

## 实施分段与验收

一轮交付按下列顺序完成；每段保持可验证，不以只改工具名称作为抽象完成。

1. 定义公共契约、可选适配端口、当前回复授权与跨目标 grant；用不含飞书字段的测试适配器验证上层可替换。
2. 实现操作服务、持久化回执、媒体文件解析和飞书 send；通过工具调用完成图片、文件、引用、话题及获授权的主动发送。
3. 接入 targets、history 及消息表情/撤回/status；适配器缺少的动作不出现在工具 schema 中。同步管理端授权入口、工具目录和渠道帮助的真实支持范围。
4. 在用户企业测试渠道实测，确认无重复发送、目标隔离、错误提示、取消/超时及账号重连；确认企微收发与流式表现未改变。

必须覆盖：普通控制台默认无工具；渠道普通用户不能借账号所有者权限跨聊；当前回复与历史读取分权；同名目标不猜测；无附件入站后生成文件仍可发送；跨 Run/进程恢复不会盲目重复发送；部分失败能识别已发项；账号停用立即拒绝；引用不越目标；平台拒绝和空历史可区分；飞书真实图片/文件/引用/主动发送；企微原有回归。

后续接企微时只新增/注册该渠道的操作适配器及能力声明，并单独验收平台约束。调度触发、完整通讯录、编辑/置顶、音视频原生消息、卡片编排是后续可扩展项，不影响三个工具及公共服务边界。
