## 实际结果与供应商顺序

本轮使用同一份46页北京延庆扫描合同，通过生产 `POST /api/v1/chat/stream` 路由、真实 Agent 装配和本地配置的 DeepSeek 模型测试。测试在受保护的 SQLite 快照中运行，保留生产权限、工具和事件处理；请求只加载 `builtin:document`，不改变用户 Agent 或全局配置。明确要求模型按 `next_read` 读取至 `has_more=false`。

| 供应商 | 本轮新请求与 Agent 结果 | 全文读取次数 | 耗时 | 判定 |
| --- | --- | ---: | ---: | --- |
| PaddleOCR-VL-1.6 | 返回46页；Agent读完缓存再回答 | 6 | 45.328秒 | 实际链路通过 |
| GLM-OCR | 返回46页；Agent读完缓存再回答 | 2 | 64.693秒 | 实际链路通过 |
| MinerU 精准VLM | 上传、查询接口返回200；原任务持续 `pending`，900秒超时，未返回正文 | 1次解析调用，0批正文 | 900.012秒解析等待；929.964秒Agent结束 | 实际解析未通过 |

MinerU另外使用635字节、答案确定的单页PDF直接调用生产适配器，仍持续 `pending`，900.003秒超时。这说明本轮失败并不只发生于长合同；凭据和任务入口接受请求不等于解析可用。没有重新提交同一付费任务、切换接口或回退其他模型。Agent超时后自行查询其他信息并结束，不能把最终 `completed` 当成合同解析成功。

供应商选项统一按 **PaddleOCR → GLM-OCR → MinerU** 排列。未配置时编辑弹窗默认选Paddle；已保存供应商不自动改变。本轮可用性及前期测试支持这一暂定顺序，但样本量不足以证明长期稳定性或SLA。

## 已修复的问题

| 问题 | 修复后的行为 |
| --- | --- |
| 同一个远端任务被模型重复等待，每次重新获得900秒 | 当前Run同文件、供应商和模型共用首次提交的900秒截止时间；恢复只用剩余时间，耗尽后不再等待或重提 |
| 供应商覆盖完整容易被误认为模型已读完正文 | `has_more=true`明确提醒按`next_read`续读；指定页范围读完也不表示全文读完；保留原生正文 |
| 历史重新显示已被ModelRetry移除的工具，并标成完成 | 对话投影过滤`removed`；运行中工具、结果和轨迹原始事实继续保留 |
| 工具等待显示成竖线 | 修正圆形spinner的盒模型和尺寸；浏览器验收见此前会话复查报告 |
| GLM服务大小／页数限制未按类型区分 | PDF最多50MB/100页，PNG/JPEG最多10MB；配置说明与校验一致 |
| MinerU上传结果不明后遇`converting` | 识别原任务已接受文件，继续查询，不重复上传或提交 |
| 空上传索引、空任务状态、Paddle异常页面结构抛内部异常 | 明确返回`invalid_result`；有效原生Markdown和页序保留 |
| 并发保存保留Key时覆盖另一请求刚更新的Key | 在现有数据库写事务中读取、合并和保存配置；沿用既有写锁，无DDL |
| 全局工具设置两张内卡片；对话附件增加下载入口 | 一张卡片两行，无分割线；移除对话附件下载入口，图片预览和轨迹下载保留 |
