# 业务助手初始化与升级

状态：**讨论稿，未实施**。首次整理：2026-09-10。当前代码基线：v0.9.2，数据库 Head 002。

## 建议结论

将“部署时塞几条配置”收口为“业务助手包的安装与升级”。

- 电子表格、DeepCube 项目分别维护并发布自己的提示词、Skill 和 UI 工具。
- DeepAgent 提供统一的管理员安装入口，负责固定 ID、校验、文件落地、冲突处理和安装记录。
- 环境管理员选择安装版本、模型和 MCP 绑定；普通浏览器打开业务页面时不执行安装或升级。
- Skill ZIP 仍存目标环境 File Store。发布原包另按版本留存，不能只保留当前安装文件。
- 首版采用后台手动入口；未来部署自动化调用同一安装服务，不另写一套 SQL 初始化。

v0.9.2 的空库初始化只提供 DeepSeek/default 等基础配置，**不等于安装电子表格或 DeepCube 助手**。
默认模型尚无 API Key，也不能直接当作业务助手已具备运行条件。

## 谁发布、谁安装

| **参与方** | **负责** | **不负责** |
| --- | --- | --- |
| 电子表格项目 | 电子表格助手包、业务 Skill、UI 协议与兼容测试 | 在普通用户浏览器里自动覆盖后台配置 |
| DeepCube 项目 | DeepCube 助手包、脚本 Skill、编辑器交互协议 | 决定其他环境使用的模型 UUID、密钥 |
| DeepAgent | 安装预检、受控指定 ID 创建、升级/修复、资产归属、状态和审计 | 替业务方维护最新版 Skill 正文 |
| 环境管理员/部署流程 | 选包和确切版本、模型/MCP 绑定、授权新增能力、决定升级时间 | 从 Test 全量复制密钥或会话作为产品默认值 |

首版建议只内置两个助手的目录信息与稳定身份；发行包由业务构建流程生成，管理员上传安装。
“检查升级”需有可信发布源才支持在线比较；发布源未定时使用“上传新版包”，不做虚假的在线检查。
发行包随业务版本交付，DeepAgent 不扫描用户浏览器缓存，也不追逐不受控的 `latest`。

## 管理员看到什么

入口建议：Console 中的“预制助手”目录，和普通 Agent 管理区分开。

```text
电子表格智能助手  未初始化      [初始化]
DeepCube 助手      已安装 1.2.0  [上传新版包] [修复] [更多]
```

“初始化”先选择发布包和当前环境模型，核对所需 MCP/UI 工具/Skill；缺凭据或依赖时显示“待配置”并停止预检。
首版不为此创建一个无法运行的 Agent。配置补齐后再次确认安装。

| **操作** | **建议语义** |
| --- | --- |
| 初始化 | 固定 ID 创建 Agent、安装本包资源；重复执行不重复创建，不覆盖已安装配置 |
| 升级 | 应用确切版本的业务资产，保留环境绑定；先展示差异和新增权限，有人工修改则阻止静默覆盖 |
| 修复 | 按已安装版本补回缺失 Agent/Skill 文件，保留安装时绑定与后续环境设置；绑定已失效则提示重新选择 |
| 恢复默认 | 经确认恢复已安装版本的受管理提示词、资源和关联，不恢复密钥、不删除会话；不是升级至最新版 |
| 停用 | 阻止该助手发起新 Run；不自动重建、不删历史，客户端明确提示未启用 |
| 卸载 | 独立高风险入口；检查业务入口和资源引用，首版有历史/共享引用时建议阻止物理删除，改用停用 |

“预制不可普通删除、允许停用”是拟新增能力，不是现有行为。入口拦截须覆盖 REST/SSE、恢复执行和渠道，
不能只把 Console 按钮隐藏。停用时已有运行如何处理需确认，建议先排空再停用，不强杀。

## 助手包交付契约（拟定）

一个业务助手一个版本包，包内包含：

```text
manifest.json       业务编码、固定 Agent ID、包版本、文件 Hash、兼容要求
agent/prompt.md     标准提示词
ui-tools.json       本助手自有 UI 工具定义
skills/*.zip       本助手上传型 Skill 原包
```

包内不得包含 Provider API Key、MCP Token、Test File ID、会话数据或目标环境模型 UUID。
内置 Skill 只声明编码和兼容要求，不重复上传。开场白若只属于业务前端，不搬入 DeepAgent 安装记录。

| **字段** | **建议约束** |
| --- | --- |
| `package_code` / `owner` | 稳定业务编码和维护方，如 `deeptable-assistant` / `element-deep-table`；名称不能替代归属验证 |
| `version` / `sha256` | 包版本与内容校验分开；同版本不同 Hash 报冲突，禁止原地替换发行包 |
| `agent_id` | 使用上述既有 UUID；升级不换 ID、不删后重建；部署前与实际业务入口再次核对 |
| `skills` / `ui_tools` | 精确资源编码、版本、文件与 Hash；不能越权接管其他业务同名资源 |
| `requires` | DeepAgent 和业务前端协议兼容范围、模型能力、内置工具及 MCP 需求 |
| `managed_fields` | 本包拥有的字段/关联范围，不能指定密钥、环境模型等保留字段 |

名称相同但 ID 不同、ID 已被其他对象占用、资源编码归属不明，都必须报告冲突。
已有 Test/客户环境中的同 ID 助手不自动纳管；管理员预览差异后显式“接管为预制助手”，保留原配置快照。
首版继续让客户端使用固定 UUID，不强制改造所有聊天接口为业务编码寻址。

## 安装与升级链路

```text
业务项目构建并发布版本包
  → 管理员上传，预检格式/兼容/资源归属/环境依赖
  → 选择模型与 MCP，确认字段差异及新增权限
  → 排空相关运行，锁定本次安装对象
  → 上传新 Skill 原包，校验并准备运行文件
  → 单事务切换 Agent、Skill、UI 工具与安装记录
  → 核验读取与运行就绪，解除安装门禁
```

- 不要由浏览器依次调多个 CRUD 接口来“模拟原子安装”，需要后端安装服务编排。
- 确认请求必须绑定预检的包 Hash、目标配置版本与模型/MCP 绑定，防止预检后配置已变化。
- 包校验必须沿用 ZIP 大小、路径穿越、Hash、Schema 等边界；安装不能执行包里的任意脚本。
- 新文件上传失败不改当前配置；数据库失败回滚并清理本次新文件，不能删除已有文件。
- 数据库已提交但运行目录未就绪时显示“待修复”，阻止新 Run，不能谎报安装成功。
- 一个 Skill code 当前只有一个有效版本，且可能被多个 Agent 引用；升级前必须列出全部受影响对象。
  首版业务 Skill 各自拥有独立编码；真正共享 Skill 由唯一维护方发布并检查所有引用方兼容性。
- 首版按受控单实例维护窗口执行。多 Pod 自动滚动升级不纳入本期承诺，后续必须有运行副本就绪屏障。

## 更新与本地修改

安装记录保留“上次应用的业务基线”；升级比较旧基线、当前配置和新包。
首版只做确定的差异/冲突提示，不自动合并提示词，也不静默扩大工具授权。

- 包管理：标准提示词、自有 Skill/UI 工具及明确归属的关联。
- 环境管理：模型选择、Provider 密钥、MCP 地址和凭据、管理员追加配置。
- 旧版本 → 新版本：无冲突时确认升级；已是更高版本时禁止自动降级。
- 同版本同 Hash：不重复写入；文件缺失走修复。
- 人工修改了受管理字段：提示保留、显式覆盖或复制成独立定制助手；默认不覆盖。

File Store 保留目标环境的安装文件，不复用来源环境的 File ID。
业务制品库保存不可变发行原包；安装器还需保存当前及至少上一版本的可恢复快照/原包引用。
不能直接依赖现有 Skill 替换 API 的旧文件删除策略完成回滚。
回滚是显式切回已留存版本，仍需校验前端协议和资源引用，不等同于数据库 downgrade。

## 数据与接口边界（待设计确认）

本课题实施时建议新增安装记录和版本/资产归属记录，**需要新增数据库迁移**；本轮没有创建这些表，Head 仍为 002。

| **对象** | **至少保存的事实** |
| --- | --- |
| 助手安装记录 | 全局唯一业务编码、固定 Agent ID、已安装版本/Hash、状态、环境绑定、乐观锁版本 |
| 发行/应用快照 | 版本、包原件引用、上次应用的受管理基线、资源清单/Hash、操作者和时间 |
| 资产归属记录 | 资源类型/编码、维护方、所属包与应用版本；共享资源不能由两个包各自覆盖 |

作用域先沿用当前 Agent 全局语义，不擅自增加 App/Space 多实例。若未来要同一业务助手多套配置，另议业务编码到本地 ID 的解析。
旧 Agent/Skill/会话不整体迁移；仅用户确认接管的资源进入安装记录。不要复用会话 Event Store 存安装日志。

拟议接口组（名称尚未定稿，不是现有接口）：目录/状态查询、包预检、确认安装/升级、修复、恢复默认、停用/启用。
确认写入仅允许企业管理员或未来明确授权的部署身份；预检结果提供冲突、缺依赖、影响范围和预计变更。
相同确认重试必须幂等，冲突返回明确冲突原因，失败不得用“已安装”掩盖部分完成。

## 首版建议与待决问题

首版只做两个助手的统一包规范、管理员上传预检/安装/升级、显式接管、修复、字段保护和安装状态。
不做在线市场、浏览器自动更新、多版本同时运行、跨环境复制密钥或后台静默追新。
后续部署自动化和在线版本发现复用同一服务。

建议先确认四点：

1. 两个助手都保留目前清单的 UUID，首次安装绑定本环境已配置好的模型。
2. 业务仓库发布包，首版由管理员上传；是否已有可复用的业务制品库，之后再接“检查升级”。
3. 官方管理字段有人工修改时默认阻止覆盖；深度定制复制为普通 Agent。
4. 预制助手普通删除受保护，首版停用/修复优先，卸载和多实例另行明确边界。
