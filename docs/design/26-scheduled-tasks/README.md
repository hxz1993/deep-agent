# 定时任务

首次研究：2026-09-14。最近讨论：2026-09-16。状态：**平台自动化任务方案讨论中，尚未开发**。

最新补充：Console 只作配置/诊断，业务结果应交付到群或业务系统；优先评估现有数据流/工作流触发统一 Agent 执行入口。固定后台凭据是可评估方向；会话新建/复用及跨周期去重重新按场景讨论。最新依据见 [平台自动化任务讨论](platform-automation-discussion.md)，以下保留前轮基线，不能将“每次新会话、不做渠道投递”继续当作已锁定边界。

## 前轮基线（最新调整见上）

当前首版建议：**一条任务绑定一个 Agent、一个平台用户和明确的业务作用域，每次触发都新建会话**。服务器直接执行，不要求用户在线、有客户端或已有会话；不查找“最新会话”，不续接历史会话。

建议保留统一「定时任务」管理页，同时在 Agent 详情提供该 Agent 的任务入口。两处管理同一套任务记录，Agent 内创建时预填 Agent。入口位置尚未最终确认，不把两个入口做成两套功能。

平台用户决定会话归属和查看权限；执行身份决定数据与工具访问权限；邮件等收件人决定结果送给谁。这三个概念允许相同，但不能因为选了接收人就自动获得其身份或权限。首版执行身份优先沿用目标用户，后台授权方式还需核验。

Pydantic AI / Harness 可以承担 Agent 执行和部分运行持久化能力，但没有可直接挂载的完整定时任务产品模块。Pydantic AI 官方提供 Prefect 等持久执行集成，日历调度和停机处理由这些外部系统负责。首版不必为了定时功能升级框架或引入整套外部工作流平台。

已认可的补跑方向：**每个任务错过再多次，也只合并补一次**，随后回到正常时间表。此前“一小时有效期、skip/latest 多项配置”属于早期建议，当前首版不强制增加。人工暂停不补、同任务不并行等为建议默认规则，详见设计。

候选场景包括预算指标监控、异常预警、定期报告和邮件发送，尚未选定首个验收场景。新建会话留痕与主动发送通知分开处理，不把“会话已生成”当成“用户已收到邮件”。

## 产品视角回顾（2026-09-16）

对开发的一句话：用户配置“哪个 Agent、为谁、在哪个 App/Space、什么时候、做什么”，服务器到时间主动执行，创建属于目标用户的新会话，并记录本次结果；用户不用在线。

| 概念 | 产品含义 |
| --- | --- |
| 定时任务 Task | 一份可修改、暂停、删除的工作安排；如每天 09:00 做预算巡检 |
| 一次运行 Task Run | 某个计划时间实际触发的一轮，有开始时间、状态和错误；不能与任务定义混为一条 |
| 会话 Session | 本轮 Agent 思考、工具调用、结论和产物的记录；既有方向是每次新建 |
| 结果投递 Delivery | 把结果发给谁、通过什么渠道、是否送达；与执行成功分开，首版不必强制主动通知 |

简单链路：配置任务 → 保存时间规则 → 后台到期触发 → 校验身份和业务作用域 → 复用现有 Agent 执行 → 新会话与运行记录 → 按已配置能力投递结果。

既有方向仍为每次新会话、用户离线也能执行、错过多次合并补一次。一次性/循环、统一管理入口、暂停/立即运行、同任务不并行、人工暂停期间不补等仍是助手建议默认值，详见设计，不因本次整理自动变成已批准需求。

与 Sandbox 独立：调度负责“何时做”，Sandbox 负责需要脚本时“在哪里做”；纯 MCP 查询无需等待会话级 Sandbox。定时等待不占用一个常驻沙盒；每次新会话默认也不继承上次临时目录。跨周期指标比较/告警去重应使用明确业务状态或权威数据，不能依赖可能过期的环境。

继续讨论应先区分三种诉求：到点提醒用户、到点自动分析并留结果、到点执行且主动发送结果。原课题重点为后两者。后台长效授权仍需核验：已有渠道 X-Deepfos-Key 方案可作为凭据候选进行评估，但空间 Key 不自动等于指定平台用户身份或所有工具的授权，不能直接复制浏览器 Cookie。

本次未刷新上游仓库或重新声明框架“最新”能力；外部实现证据仍按调研文档的 2026-09-14 版本基线理解。下一步可以先用一个具体业务例子确定“做什么、结果归谁、是否通知”，再由研发核验授权与后台工具可行性，不要求产品先选择 Cron 库或调度框架。
