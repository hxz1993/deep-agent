### ZIP 外层时间戳测试维护

后续完整封板发现，原测试错误地要求两次正式导出的 ZIP 外层字节完全相同。生产 `ZipFile.writestr` 使用各次真实导出时间，跨 ZIP 的两秒时间窗口后，即使配置与资源完整内容未变，外层时间戳和整包 SHA256 也可不同。这不影响关闭输出包的旧版安装兼容。

测试改为直接打开两份未修改的正式导出物，严格比较有序成员名、每成员完整原始字节、未压缩大小、CRC、压缩方法、完整 manifest 及每成员 SHA256。忽略的只有不属于配置内容的 ZIP 外层时间戳；没有修改生产打包、冻结跨进程时间、手工重拼包或使用新版解析器代替旧端。两份原始 ZIP 仍各自完整执行旧端预检、新建、覆盖、资源复用和聊天。

修改后同一 6 组方法 7.140 秒通过；随后按完整 unittest discover 原序执行到该方法，20 方法 17.845 秒全部通过，包含旧有正式双 TCP 12 组矩阵，无 skip。生产代码和数据库测试未变，本次不重跑已完成的真实 48 数据库方法。各原始 ZIP 指纹和成员 SHA 单独记录，不能把某次碰巧相同的整包 SHA 作为兼容契约。

### 最终关系的并发补查

首次子表版本 48 方法通过后，存储审查发现 MySQL REPEATABLE READ 事务可能保留父行初读时的旧政策。新增服务数据库专属屏障：先暂停 Schema/提示词修改者的第一次普通 Agent 读取，让另一事务先将政策改 true 并完成提交，再放行前者；它省略政策字段，必须保留已提交 true，且保存返回值与全新连接回读一致。MySQL 还实际查询并断言隔离级别为 REPEATABLE READ；SQLite 的整段写会话串行不能代替该竞争验证。

加上锁后读取当前配置的补丁后，真实 MySQL 独立新 013 方法 4.546 秒仍精准复现：Schema 后写分支通过，提示词后写分支数据库子表及 fresh Agent 为 true，但 Store 返回 Agent 的计算属性仍为 false。测试保留 `False != True` 失败及完整屏障证据，不把仅数据库正确计为保存回显正确。存储负责人在 refresh 后使用 SQLAlchemy 的 `set_committed_value` 同步锁到的最终只读政策，不写 Agent 物理列；同一实际 MySQL 用例以原断言复验，1 方法 5.423 秒通过，无 skip。

补丁后已实际重新完整执行 MySQL/PostgreSQL 各 24 方法，以及 SQLite/正式跨版，最终结果见上表；没有以修复前绿结果代替。失败日志保留 `first-mysql.log`，修复前完整数据库结果保留 `before-race-*`，最终全量实库日志与结果独立保存。

### 未发布旧候选的排障经过

两方言首轮各实际执行 24 方法，包括渠道引用事务 9、逻辑引用 8、MCP 引用 3、旧迁移 1、配置导入 1、原结构化输出 1、新 013 1。不是只跑新增迁移，也未将另一方言 skip 计入。

首轮两种错误分别处理：

1. 两方言的旧配置导入测试在真实 012 结构上用当前 ORM 全列读取，新增列不存在。修复测试夹具读取方式并将当前 ORM 阶段移至全部历史 012 断言之后；未改成全程 013，也未删除原始 Unicode、回滚、记录锁或同 Revision 断言。
2. MySQL 连续 013→011 降级时，013 的 DROP COLUMN 隐式提交，后续 012 保护拒绝导致版本标记仍为 013；第二次尝试报缺列。这是实际迁移阻塞项，交由存储实现负责人修复事前保护。独立测试增加首个拒绝后重新连接读取版本、物理列及两份定义的断言，必须保证拒绝零部分变更，不能只改预期或跳过。

原落点第二轮 PostgreSQL 24/24、35.604 秒，无 skip；MySQL 23/24、36.860 秒，无 skip，旧导入和真实降级阻塞均修复通过。MySQL 唯一剩余失败是测试假定两次保存跨秒，而既有 DATETIME 仅秒精度。测试已改为预置固定 2020 年旧时间，正式只更新政策并由新 session 读回时间与操作者，保留严格大于旧时间断言。原落点末次复跑接到用户暂停后主动取消，不能计通过；容器、子进程和凭据已清理。

原 SQLite 两方法 6.009 秒通过；完整 discover 导入后单方法 2.266 秒通过、按真实前序执行到该方法 22 方法 36.363 秒通过（2 项缺服务器 URL 跳过，不计数据库实测）。保留冻结 SDK metadata 独立 SQL 读回 true 后应拒绝降级的原断言；首轮全量在早期夹具编辑期间启动的失败不能用删断言处理。原正式旧端六组 8.293 秒通过。

首轮失败、原落点复验与最终落点结果分开保存。只有最终配置表实现就绪、重新完整执行两方言 48 方法及 SQLite/正式跨版，并确认所有清理完成，才可签发该门禁。

## 数据库断言

- 从真实 012 物理结构升级 013，仅 `agent_output_configs` 增一列，Agent 物理列完全不变，没有新表/结果事实源。非空、数据库默认 false、应用默认 false；真实 012 历史定义和 raw SQL 新插入定义均为 false，历史 Unicode 原始事件保持。
- 没有输出配置行时，政策视为 false；不能为了 true 政策创建空定义。无定义的 true 创建或更新在正式 API 返回 422，原记录、时间、操作者和配置行均不变。关闭总开关但带合法定义时，允许保留 true 草稿。删除定义且省略政策时归 false；明确 true 同时删除定义仍拒绝。
- 默认严格、开启混合、关闭但保留 allow_text=true 定义草稿均独立保存。普通 PATCH 省略新字段保持原值；只改政策也记录可信更新人和时间。
- 真实事务在子定义 flush 后故障，开关、allow_text、完整定义、更新时间、更新人一起回滚；由新 session 重新读回，不只检查事务内对象。
- 真实 012 备份识别/同 012 恢复不要求输出配置的新列；跨 Revision 仍明确拒绝。013 备份只在子表行保存政策，不向 Agent 行注入新键；关闭草稿及政策恢复到同 013 后三种状态、Schema 和原更新人完整，不复制聊天/运行事实。
- 013→012 有 true 配置（包括关闭草稿）时拒绝；当前输出配置政策清 false 后，真实 SDK 用户事件的冻结 contract=true 仍阻止降级。没有新政策事实时允许去掉子表新列，重新升 013 后默认 false、原配置与历史保留。多段降级被后续 012 保护拒绝时，013 版本、子表政策列和两份定义均不得部分变化，Agent 不得出现政策列。
- 客户业务元数据中同名 `allow_text_output:true` 不是平台冻结政策，不应误拦。审查发现最初递归扫描过宽后，由存储实现负责人限缩到 SDK metadata 的 `deepagent_output_contract` / `deepagent_output`；本组使用原生 Pydantic 消息序列化和真实 Event 包装验证。

SQLite 通过不能替代真实 MySQL/PostgreSQL；两个服务方言执行与 skip 数在最终结果中单独回填。
