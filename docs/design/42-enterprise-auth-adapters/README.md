# 42 · 企业集成与鉴权适配器

> 整理日期：2026-11-05。
> 状态：讨论归档、后续设计，**尚未实施统一适配器、管理界面或热重载**。
> Python／Skill 的可选非凭据上下文已纳入 v0.15.6；统一鉴权适配器仍为后续设计。数据库 013，依赖不变。

## 结论与职责

未来将客户账号映射、Token 兑换及凭据刷新收敛到服务端的统一企业接入层，供 MCP 和 Skill 共用。
客户差异放在可维护的适配器中，不把客户字段、固定账号或分支散落到通用 Harness。
部署优先复用 DeepAgent 服务，是否需要独立进程只按实际运行要求决定。

当前 `include_context` 只决定脚本是否看见非凭据用户资料，**不承担鉴权开关或授权证明**。
未来鉴权方法即使在 `include_context=False` 时，也应能使用宿主已经确认的当前身份。
模型可以选择调用哪个已授权服务，不能通过填写 username／JSON Context 决定以谁的身份访问。

| 调用情况 | 当前处理 | 后续统一能力 |
| --- | --- | --- |
| 固定服务身份 | MCP 固定 Header；Skill 自行读取随包 `.env` | 可继续沿用；需要集中维护时再接凭据管理 |
| 平台内部接口按当前用户访问 | MCP 保留现有 inherit／isolated；本轮不向脚本透传平台凭据 | 宿主提供平台请求方法，使用本次可信鉴权，不要求全经过 MCP |
| 客户个人权限／SSO | 个别 Skill 取得当前用户资料后填写客户要求的账号字段，客户固定 Key 仍单独管理 | 统一账号映射、换票、Token 缓存及 MCP／脚本接入 |

客户只有“共享 Key＋域账号”的接口时，适配器可从可信平台身份得到客户账号，再组成请求；
客户要求用户级 Token 时，适配器按其认证协议兑换。两者都是目标接口的适配，不要求所有客户先建设 OAuth。

## 当前已确定的上下文契约

普通 `execute_python` 和 `execute_skill_script` 均为 `include_context=False` 默认关闭；
Agent 在调用需要用户资料的脚本时显式开启。原生与 PTC 共用实现，不加 Skill metadata，暂不新增 `get_current_context` 工具。
完整格式、失败行为和代码示例见 [Skill 指南](../../guides/skills.md#按需读取当前用户与应用范围)。

- 一个 JSON 环境变量 `DEEP_AGENT_CONTEXT`，包含公开用户资料以及本次有效的 `app/space/language`。
- 身份由后端可信请求确定；Console 调试覆盖先经既有请求上下文解析，不用模型输入替换。
- 无 Cookie、Token、API Key、任意请求 Header；不自动加载 `.env`，不自动回显身份资料。
- 资料成功但字段为空时保留空值。失败或超时时继续运行，只保留 `user.id` 和安全错误，其他业务字段为空；脚本自行判断必要条件。
- 不用 ID、昵称、邮箱或 `.env` 固定账号冒充缺失的用户名。客户账号规则不同，应明确增加映射。
- 已有脚本输入输出、模块布局、文件授权及上传流程保持；普通 Python 不因此获得 Skill 文件目录。

### 用户资料什么时候查询、缓存什么

```text
可信入口确定 user ID、App、Space、Language
  → Run 开始（此时不查询完整资料）
  → 首次执行 include_context=True
  → 查本进程的资料成功缓存；未命中才请求账号服务
  → 将本次成功／空资料／失败快照保存到 Run
  → 后续开启的普通 Python、不同 Skill、PTC 共用快照
  → Run 结束释放；下一 Run 重新进入上述判断
```

共享资料缓存是 API 进程内的短期优化，不是 Console 管理员的会话，也不依赖先打开 Console：
`/current-user` 和执行路径都通过同一个解析服务填充缓存，第一次实际需要资料的入口负责查询。
缓存只保留公开资料；成功项有效期 30 秒、最多 256 份，按账号服务环境、当前用户、有效凭据指纹和有效语言隔离，合并并发。
请求链路统一使用平台有效 `language`，不因浏览器的 `Accept-Language` 与执行白名单不同而重复查询。
鉴权原文不进入缓存键或脚本；跨 Run 不缓存失败，Run 内缓存失败以免每个脚本反复查故障服务。一次资料查询总预算 5 秒。

当前工作只是为客户适配提供非凭据资料；没有把这些资料变成任意第三方的权限凭证。

## 未来统一调用链

```text
DeepAgent 当前可信调用者
  → 统一适配服务（选择已登记服务及适配器）
  → 客户账号映射（稳定 ID／username／邮箱／域账号）
  → 固定服务凭据，或按客户协议获得短期 Token
  ├─ MCP：组成本用户的连接 Header／认证对象
  └─ Skill：宿主请求方法或执行期鉴权方法
  → 客户服务按实际账号权限处理
```

账号映射的输入来自宿主。渠道入口当前会话 owner 不一定等于实际发问员工，后续按人授权时必须明确可信渠道发送人及映射来源；
不能静默借用机器人 owner、开发者用户名或某个调试账号。本轮只防止本地开发用户名错误绑定渠道身份，未实现渠道员工到平台账号映射。

### MCP 和 Skill 尽量使用同一逻辑

| 位置 | 后续接入方式 | 共同约束 |
| --- | --- | --- |
| MCP 服务端装配 | 从可信 RunContext 调统一适配器，生成当前用户认证信息；同 Run 复用连接 | 不把用户 Token 保存为所有用户共享的静态 Header |
| Skill／普通 Python | 提供执行期方法，例如 `get_credentials(service="customer-kb")`，或更窄的 `request(service=…, …)` | 宿主从执行绑定得到用户；无需传入 username、Token 或 Context 才能鉴权 |
| PTC | 调用同一个 Python／Skill 实现 | 不给 Monty 单独注入凭据，不创建第二套鉴权逻辑 |

上述函数仅为接口方向，**当前没有提供这些方法或宿主通信通道**。
“返回受限凭据”与“宿主代请求”尚待取舍：前者便于复用脚本原有 HTTP 客户端，后者减少凭据进入脚本及日志的机会，但增加通信与接口适配。
不对任意 `requests.get()`、内网 IP 或路径前缀自动补平台 Header；调用者必须明确选择已登记的目标服务。

Token 不是原则上每次调用工具都兑换。按服务、用户、授权范围、凭据／配置版本及服务端到期时间缓存，提前刷新并合并并发；
无有效 Token 才取票，失效重试和业务写入重试分开。具体 TTL、刷新与撤销依据目标协议，不套用当前资料缓存的 30 秒。
跨用户或跨客户不得复用 MCP 认证会话；适配器错误明确返回，不能换共享高权限账号继续。

## 配置、交付及更新方向

建议设一个企业接入配置概念，集中维护服务地址、适配器、认证参数／秘密引用和映射规则。
MCP 与需要访问该服务的脚本引用同一连接，避免各 Skill 重复写换票代码。
具体放在现有集成配置还是独立入口尚未确定；本轮不新增字段、表、配置 UI 或插件包规范。

适配逻辑希望可版本化安装／更新，减少改主程序和重启整套服务；这与上传一个可执行 STDIO 包并不等价。
任意 STDIO 包还涉及依赖安装、进程管理、权限、健康和回收，当前不作为快捷落地方式。
后续更新机制至少需要明确：校验后激活、新 Run 采用新版本、已开始 Run 固定版本、多 Pod 一致性及回滚。
这些是评审要求，**不是已具备的热重载功能**；凭据存储同时衔接 [31 凭据加密课题](../31-credential-encryption/README.md)。

## 与后续沙盒的关系

当前每次执行按私有参数传入环境，未来可映射到沙盒的每次 exec 环境；不得把用户资料写入跨用户复用的常驻容器全局环境。
如果实现执行期鉴权方法，则需另设计沙盒到宿主的受限通信、执行绑定、超时、取消和脱敏；不能把本机进程内函数当成远程沙盒已经支持。
`include_context` 保持资料披露选项，不阻止未来统一鉴权接入。沙盒主方案见 [07 课题](../07-python-sandbox/session-sandbox-design.md)。

## KMP 短期适配与验收边界

KMP 的固定 `authKey` 继续来自 Skill 自读 `.env`；请求 `domainAccount` 取本次 `DEEP_AGENT_CONTEXT.user.username`，
删除旧包的 `CONTEXT_USERNAME` 配置与优先级。查询目录不需要个人身份时保持默认关闭，按人搜索及其入口调用显式开启。
缺变量、JSON 无效或用户名为空时，在调用客户业务接口前停止并给出清晰错误，不改用其他账号。
若平台 username 与客户域账号不一致，现场先确认映射规则，再单独实施，不让模型猜账号。
