## 当前状态与建议顺序

DeepAgent 已实现企微 AIBot WebSocket 渠道、公共 Gateway、入站去重/执行记录、会话绑定及平台身份边界；飞书和个人微信尚无 Adapter。已有微信调研仍有效，不能把“可扩展”当作“已接入”。

微信已有用户讨论和专项调研，飞书此前没有形成接入方案。上次复盘提出“先飞书”只是代理建议，不是用户确认的顺序；本课题以已有微信研究为主体，飞书仅保留候选参考。飞书企业应用长连接与企微模式较接近；微信另需扫码、登录失效、游标和回复上下文设计。凭据加密可先于两者落地，UI 同 Run 不应成为普通文本渠道上线的前置依赖。

## 三种渠道的差别

| 渠道 | 接入与回复 | 首版边界建议 |
| --- | --- | --- |
| 企业微信 | 现有官方 AIBot SDK / WebSocket，已有流式回复 | 保持现有能力，补部署真实验收；不要因新渠道重写现有链路 |
| 飞书 / Lark | AstrBot 使用官方 `lark_oapi`，支持 socket 和 webhook；卡片更新承载流式回复 | 优先长连接，不先增加公网 Webhook；App ID/Secret、消息权限、接收事件及应用可用范围需配置；流式需 cardkit 权限，否则明确采用普通最终回复 |
| 个人微信 | 扫码取得登录态，HTTPS 长轮询；AstrBot 本地 Adapter 不支持气泡内流式更新 | 先私聊、最终文本回复和已验证媒体；不承诺群聊或任意主动外发。保存登录态、游标和回复上下文，重启/失效路径单独验收 |

微信现有权限与服务端发送边界仍需真实账号验证。腾讯插件协议并非完整服务端契约；不能从客户端发送函数推断可以无限主动发送。详细依据见 [微信研究](weixin-astrbot-research.md)。

## AstrBot 值得吸收的设定

1. **按渠道显示配置。** 类型注册携带配置模板与能力信息。飞书用 App 凭据、微信用扫码，不强制所有渠道填写同一套 Bot ID/Secret。连接高级参数用合理默认值，不把全部超时暴露到普通表单。
2. **区分机器人、对端会话和发送者。** UMO 使用机器人实例、消息类型、对端 ID 组合。DeepAgent 已有 Account＋Peer 绑定，沿用即可；名字相同不表示同一人。AstrBot `unique_session` 还能在群内按发送者隔离历史，正式接群前应明确采用群共享还是每人独立，不能隐式切换。
3. **能力决定回复方式。** 飞书卡片支持增量更新；个人微信采用最终回复或克制分段，不假装所有渠道都能流式。模型的内部思考和完整工具参数不默认对外发送。
4. **唤醒、访问限制与速率控制。** AstrBot 有群唤醒、回复 @、白名单/权限和频率设置。我们应先明确允许谁使用、群内何时响应，以及平台执行身份；不照搬其全部开关。渠道用户识别不等于 DeepFOS 业务授权。
5. **凭据与运行状态生命周期。** 扫码结果自动保存，重启复用有效登录态；状态区分配置成功、连接成功与业务发送成功。微信游标、重复消息、消息已执行但发送失败要验证，不能用简单重试重做写业务操作。

不引入 AstrBot 整套插件宿主、不另建模型历史库、不搬其明文 JSON 凭据保存方式。UI 工具的浏览器表单也不会自动变成飞书卡片：若渠道需要交互审批，应另设计具体映射，不默认支持全部 UI 工具。

## 真正需要定下的最小范围

- 一个机器人绑定哪个 Agent、哪个平台执行身份；首版仅管理员配置身份还是必须逐人授权。
- 私聊/群聊与群内历史隔离；是否仅 @ 才响应。
- 文本、附件、最终回复/流式卡片的首版清单。
- 登录/解绑/凭据失效、断线重连、重复入站、投递失败与重启恢复。

优先保留简单配置和可复用的 Adapter 边界；多副本、主动通知、定时任务仍由各自课题决定，不绑进第一版渠道接入。
