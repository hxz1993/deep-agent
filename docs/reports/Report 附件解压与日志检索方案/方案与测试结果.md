# 附件解压与日志检索：隔离测试和改进路径

2026-09-15。本次仅研究本地上游源码、创建独立 Agent 和调整其提示词；不改产品源码、原工单 Agent 或 Skill，不推送。

## 建议决定

保留 `read_file` 的通用局部读取职责。当前用短提示词 + 现有 `execute_python` 做解压、完整扫描、统计和异常分析。若进入产品完善，优先设计独立 `search_file`，用于确定性的关键词/正则定位及上下文返回；不要先创建日志专用工具包或 RAG 系统。

“能运行”与“稳定交付”必须分开：样例已能运行，短提示词不能保证文件参数、扫描方式、输出预算和结论准确性。完善顺序应为：

1. **附件执行契约**：原附件 ID 到沙箱的挂载和取路径清楚、一致，遗漏挂载有直接可修正的错误；确认生产上传链路返回可读原字节。现有 `execute_python(files=...)` 可以完成，本次不增加新接口。
2. **通用搜索工具（首选新增项）**：按已授权附件 ID 搜索，支持字面/正则、上下文、条数和字符预算；返回行号/字符位置、扫描是否完成、命中数或未完成状态、续查游标。完整总数只能在完成扫描后声称；分页数量不能当总数。复杂聚合留给 Python。
3. **归档与产物复用**：第一阶段仍由 Python 按需解压，结果可用已有 `publish_path` 保存为产物供后续使用；重复查询明显时再实现缓存/索引。若要承诺所有压缩包的稳定解包，需要工具层受控的归档目录/解包操作，硬限制累计解压量、成员数、嵌套深度及路径；不是继续给系统提示词加句子。此项属于待确认的后续开发。
4. **统一返回预算与证据**：当前沙箱已有 stdout/result 硬截断，但模型可输出远多于提示词约定的内容。需要可配置的较小结果预算、完整结果产物引用、可定位的原文入口。不要把正常截断误写成完整扫描结果。

`execute_skill_script` 目前仅挂载同 Skill 资源，没有会话附件 `files` 参数。因此以后选择预制脚本路线，须补附件桥接；本阶段不修改 Skill，也不以安装脚本包就能解决为前提。

## 测试对象和边界

- 新建 Agent：附件解压与日志分析测试，仅 `builtin:sandbox`，无 Skill/MCP；DeepSeek flash。
- 保留较短的第一版提示词，263 字；只约束先程序扫描、少量证据、文件参数及事实/假设区分。
- 原 ZIP → 单个 GZ → 6,766,228 字节 UTF-8 日志。基准：3745 行，INFO 2811、ERROR 9、WARN 2。
- 大包为该 GZ 的 20 个明确副本：压缩约 8.4 MB，解压共 135,324,560 bytes（约129 MiB），74,900 行、180 ERROR、40 WARN。它验证多文件容量，不代表20种真实日志格式，也不代表单个129 MiB巨型文件。
- 本地 API 仍拒绝 ZIP MIME。为隔离“上传之后”的执行能力，测试脚本通过本地 FileStore 登记真实 ZIP 字节与当前所有者，再将附件 ID 交给8000聊天接口。没有改 MIME、没有把压缩字节伪装成文本，也没有修改上传白名单。不是测试环境真实端到端验收。

前三组Python累计执行各约2.4–2.6秒。输入Token分别36,622 / 50,142 / 45,416，缓存命中分别27,776 / 38,528 / 36,096；是多轮累计，不是文件本身Token或单次上下文占用。

第二版另有两次在任何工具调用前约16.6秒报模型 `Request timed out.`，没有查明根因，排除在提示词效率评价之外；复测成功但没有减少调用。第一版与原工单Agent的105秒不能当严格A/B：Agent能力、系统提示和回答深度不同，本轮样本量也不足以证明稳定性能。

发现的实际偏差：
- 第一版大包按文件依次处理，但每个成员仍完整解压到内存，并未实现提示词要求的严格流式扫描；归档预算也没成为代码硬限制。
- 第一版LOG某次回传约23,298字符，超过提示词8000字符意图。
- 第一版LOG回答把MessageSource异常的ERROR条数说错，并出现时间笔误；大包回答说“无嵌套压缩包”，与ZIP内GZ事实不一致。
- 第二版即使明确文件参数仍漏传/混用文件ID，失败2次；最终输出错误解压字节数，并把异常名称出现次数混入异常分类。
- 大包生成并再次读取JSON分析产物成功，证明现有产物复用链路可用。

## read_file 分页对照

直接调用当前分页实现对真实日志测算：limit200需165页；默认1000或最大4000均需164页。因为每页还有50,000字符限制，长行最大168,856字符。完整遍历将向模型返回约663万字符。

它适合局部证据阅读，不适合让模型逐页完成全量统计。当前实现先缓存完整字节及解析结果，再向模型分页；它并非文件系统层的流式读取。保留现有next_offset/next_char_offset，不能照搬别的项目导致长行后半丢失。
