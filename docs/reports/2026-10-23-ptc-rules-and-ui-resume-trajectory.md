## 轨迹重复行的原因与修复边界

UI 工具调用属于暂停前 Run，确认返回属于 Resume Run。原 Console 只按当前 Run 寻找实时返回的调用，漏配后追加无持久 sequence 的直播行；刷新重投影后才合为一条。后端 History、真实工具执行及最终输出接受事实没有重复，未改写这些后端逻辑。

配对优先使用持久事件的来源位置；同一轮次中只能唯一确定的待完成 Deferred 调用才允许跨 Run 配对。调用 ID 不能单独用于全局合并；来源不足或冲突时等待持久事实。持久事实替换直播行也限定同一调用身份。具体回放、选择位置、顺序、状态与计数验收结果见下文。

浏览器实测补出了第一版夹具遗漏：真实 SDK 持久 ToolCallPart 没有 `metadata.widget`，只有来源 Assistant Event 的 `status=pending`。因此不能把展示用的 `kind=deferred` 当作持久证据。最终实现读取已有 Pending 来源事实；不新增字段、不查询当前工具配置，也不按工具名前缀推断。先前五个合成红灯、真实无 widget 的红灯及后续修复日志均保留。

## 真实 Provider 验证

使用本地隔离 Agent、15 个合成回环 MCP 工具及真实 DeepSeek：

- 原生工具链正常；首次多次搜索均命中预选工具，没有新增披露，因此不把它算作多批新增覆盖。补验实际产生三批非空新增披露，随后旧原生工具与旧 PTC 目录仍可调用。
- 合法 PTC 聚合返回 `count=4,total=140`。故意 `1 / 0` 失败后仅一次原生恢复成功，没有重复写入。
- API 确认续跑后的七个真实调用均为一条 SSE Call、一条 Result、一个 History Item，未出现协议重复。该模型先误用 `status` 得到零，再在 PTC 中探查形状，最后使用 `active` 得到正确结果；三次运行成功不代表三次都遵守 PTC 使用规则。此为保留的模型行为偏差，未将只读重算误称为工具重放，也未扩大本轮为新的策略强制执行机制。
- 浏览器首轮合成 MCP 进程已退出，前置读取失败，模型没有发起确认。恢复自建 MCP 后新建会话验证；该失败保留为夹具环境问题，不记作 UI 暂停测试通过。
