# 结构化输出：响应解码失败与实时轨迹一致性修复

## 结论与边界

本地 JEV 模拟实验首轮失败发生在 HTTP 响应解压阶段，尚未进入完整响应的结构化输出校验。不是“要求普通文字就应报这个错误”。第二轮结构化输出成功；其后显示的失败助手实际属于第一轮。

保留原会话及 Agent 配置，不重放原会话，不重写历史。修复不改变 Schema、允许文本策略、纠错额度或业务工具分发，也不增加数据库结构、依赖、环境变量或自动重试。

## 原始证据

管理员 Events 完整读取 9 条、History 完整读取 4 项，诊断日志完整读取 20 条（非截断）。时间如下，均为北京时间：

| 时间 | 持久事实 |
| --- | --- |
| 22:01:59.702 | 第一轮用户输入 |
| 22:01:59.920 | 第一轮助手响应开始，最终只保存部分思考 |
| 22:02:01.255 | 第一轮 `execution/error`，类型 `DecodingError` |
| 22:02:05.999 | 第二轮用户输入 |
| 22:02:09.959 | 第二轮 `output/attempt` 已接受 |

两轮冻结契约均为严格结构化输出（旧快照缺少 `allow_text_output`，按 false）。第一轮 `rejected_responses=0`、剩余修正额度 2，没有输出尝试事件；第二轮同契约成功。由此排除“第一轮已收到普通文字并被格式校验拒绝”。

原始 Events、History、诊断日志和真实 Provider 回归响应保存在忽略的 `docs/local-artifacts/Report 本地结构化输出异常与轨迹一致性20261022/`，不进入 Git。

## 根因一：并发响应解码

本机实装 `httpx2 2.7.0` 的 Python <3.14 zstd 适配在模块级绑定同一个 `ZstdDecompressor` 的 `decompressobj` 工厂，不同响应因此共享底层解压上下文。[python-zstandard 官方约束](https://python-zstandard.readthedocs.io/en/latest/decompressor.html)要求重叠的解压操作各用独立实例。

用两份独立、合法的压缩响应，通过真实 `httpx2.Response`、`AsyncByteStream` 和并发屏障交错读取，复现了完全相同的 `Unknown frame descriptor`。串行读取、独立解压实例和 gzip 对照均正常。进一步使用真实 SDK 同时消费主 SSE 与非流式标题请求，原代码失败，修复后两者成功。

现场首轮恰有主响应和标题生成并发，第二轮没有标题任务，与上述缺陷的触发条件吻合。历史日志未记录响应压缩头或原始传输字节，因此不能追溯断言当时每一个压缩帧的内容，也不归咎于代理或 Provider 业务返回格式。

修复：模型请求通过公开 `ModelSettings.extra_headers` 协商 `Accept-Encoding: identity`，覆盖持久模型、旧 Spec 入口、标题、摘要、连接探针及订阅 Provider 装配。SDK 继续管理原 HTTP client；不 monkeypatch 第三方解码器，不升级依赖，不因部分输出失败自动重跑工具。代价是模型响应不再使用 HTTP 内容压缩，Token 与输出格式不变。

## 根因二：失败持久化事实未完整发布到 SSE

失败分支保存了部分助手，但调用 `_persist_run_messages` 时遗漏 `result_queue`，并在发终态错误前没有排空事实队列。因此数据库已有助手事实，实时 Console 却只有无 Sequence 的直播占位。

修复：失败部分响应、已有消息的状态收口均进入原 `session_event_appended/updated` 队列，在终态错误前发布。取消收口同样镜像状态更新。继续复用原事件表和协议，不新增运行回执或正常 Run 事件。

集成回归从隔离 SQLite 的独立 HTTP 连接读取 Events/History，不先 flush：先制造部分响应后解码失败，再在同会话成功续问，逐 ID、Sequence、状态与内容核对实时事实与回读结果相等；只保留一次执行异常。

## 根因三：Console 直播行替换和终态文案

Console 原先仅替换 `activeAssistantLoop`。终态错误已将其清空时，迟到的持久事实无法清除同 Run 的直播行；无 Sequence 行又被排在全部持久事实之后，造成第一轮失败助手落在第二轮结果下方。直播行时间取浏览器接收时刻，刷新则取持久 ModelResponse 时间，所以时间也不同。

修复：同 Run、同来源消息的首个持久事实替换最早对应直播行，迟到失败事实也适用；同一消息后续 Part 和状态更新不再误删下一消息的直播行。纯思考终态显示“模型响应失败／已停止／模型思考”，仅运行中显示“模型处理中”。缓存版本沿依赖入口同步更新。

保留第一轮失败助手是正确的：它表示实际收到的部分模型响应；紧接的异常行表示同一轮的执行停止，不是第二次提问又失败。History 的部分响应 `interrupted` 和事件事实的 `failed` 分别描述响应完整性和执行结果，不篡改原存储状态。

## 提示词与允许文本输出

- 未开启结构化输出：沿用普通文本路径。
- 开启且未允许文本：用户要求普通文字不能覆盖服务端契约；模型应通过输出工具给出合法 JSON，否则进入有界格式修正。
- 开启且允许文本：可正常以普通文字结束，不生成结构化接受事件或 `output_info`；JSON 分支仍完整校验。

传输解码失败早于这些完整响应判断，不能视为 Schema 拒绝、普通文字结果或已接受的业务 JSON。新失败提示明确说明是传输解码错误；SSE 错误、持久异常和部分助手诊断使用同一安全文案，刷新不改变错误解释。
