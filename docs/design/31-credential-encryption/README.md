# 31 · 敏感凭据数据库加密存储

> 2026-09-26：用户确认高优先级待办；本稿为实施边界，尚未开发。不代表当前数据库已加密。

## 目标与现状

将服务端需要再次使用的 API Key、OAuth Token、机器人 Secret 等敏感凭据改为加密落库，保持现有使用流程。当前 Provider 的 `api_key` / `credential_json`、企微应用 `app_secret`、渠道 `secret` 是首批核对对象；正式实施还需枚举集成配置及 MCP 配置中的持久认证头等实际存储入口，避免只覆盖模型供应商。

这是可解密的凭据保护，不是用户登录密码的哈希存储，也不是全库透明加密。现有列表脱敏和日志约束继续保留；不能把界面隐藏等同于数据库加密。

## 候选实现边界

- 在统一凭据读写边界采用成熟认证加密实现，不自行设计算法；具体库、密文封装及字段改动在实施时确认。
- 主密钥从独立部署 Secret 注入，不保存在同一数据库、镜像或仓库。密文带格式版本和密钥标识，支持轮换；密钥缺失或错误明确失败，不能静默当作无凭据。
- API 与 Gateway 使用一致的解密配置；OAuth 刷新、重新授权和断开仍保留版本校验，防止旧刷新结果覆盖新凭据。
- 既有明文迁移需可盘点、可重复执行且不打印内容。迁移后新写入不得退回明文；是否短期兼容读取旧明文，应有明确结束条件。
- 普通导出不携带明文秘密；物理备份、跨环境恢复与密钥备份分别规定。已有明文备份不会因新库加密自动变安全。
- 仅影响服务端持久化和部署配置，不要求业务客户端升级。数据库迁移版本在实施时决定；本次文档整理不改数据库 007。

## 验收要点

覆盖创建/修改/读取、OAuth 刷新与断开、机器人启动、密钥轮换、缺失/错误密钥、历史迁移重复执行、导出导入、备份恢复。确认数据库中无新写入明文、API/日志不泄露、错误密钥不破坏旧值。

## Dify 实现核验与可借鉴边界（2026-09-26）

核验本地 Dify `863ce1d70d829935c34b26ee9d7fb048136ea591` 的模型供应商凭据链路，不将登录密码或数据集 ID 的编码逻辑混入本课题：

- 前端 `web/service/use-models.ts` 提交凭据对象；后端校验原值后，对 Schema 标为秘密的字段加密，再写入 `encrypted_config`。不是先把明文存数据库、之后再补加密。请求在应用层包含原值，生产传输依靠 HTTPS。
- 凭据详情调用解密再脱敏；供应商列表会省略模型凭据。运行时取得可用原值进行认证。内部存在解密上下文/凭据缓存，所以不能概括为每条 SQL 或每次普通列表查询都必须重新解密。
- 编辑时识别隐藏值占位，取原凭据参与更新，不把脱敏字符串存成真实密码。DeepAgent 应沿用自身“字段未提交则不变”的契约；不因复制 Dify 方案引入额外客户端格式。
- 默认 local key provider 采用租户 RSA 密钥对：公钥在 Tenant，私钥在配置的 Storage `privkeys/{tenant_id}/private.pem`；加密格式为 `HYBRID:` 标记的 RSA 包装随机 AES 密钥＋AES-EAX 密文。还兼容旧 RSA 密文。这是两种密文格式兼容，**不是本项目明文迁移的现成实现**。
- 本地源码还存在可替换 Key Provider。我们优先借鉴密钥与数据库分开持久保存、统一加解密入口和格式可演进，不直接照搬整套租户密钥服务、Redis 私钥缓存或其异常吞掉行为。

## 历史库的推荐兼容方案

采用“先兼容读取、再统一新写入、最后迁移存量”，无需要求用户重新填写所有密钥。

| 数据状态 | 读取/调用 | 新建或重新保存 |
| --- | --- | --- |
| 明确标记的 v0 旧明文 | 服务端按旧格式读取；对外仍只给脱敏/已配置状态 | 将该记录的实际秘密全部加密后，与 v1 格式标记原子保存 |
| v1 密文 | 按格式版本和 key_id 选择密钥，验证并解密 | 采用当前活动密钥加密；格式与密文同时更新 |
| 未知版本、损坏密文、缺失/错误密钥 | 明确报错，不回退成明文，不覆盖旧值 | 修复密钥/恢复备份，或管理员明确重新配置凭据 |

建议使用显式的存储格式元数据，迁移时把现存记录确定为 v0，新记录为 v1；版本与密钥编号是存储实现信息，不给业务客户端。确切使用每记录版本字段还是每字段结构化封装，需结合字符串和 OAuth JSON 等字段清单确认。优先避免只凭字符串前缀、Base64 外观或“解密是否成功”猜明密文；字段混合格式时需逐字段标记，不能用一个已加密字段代表整条记录都已加密。

- 只读查询不偷偷更新数据库。管理员重新保存（即使未修改秘密）时，可由服务端读取旧原值并转换；OAuth 刷新也经过同一加密写入口。秘密未提交、清空、显式替换三种操作继续遵守各接口契约。
- “保存时转换”只能作为过渡，未再编辑的凭据会一直明文。另提供显式、可重复、分批的迁移任务，按记录版本/修订号做条件更新，失败保留原值，不覆盖期间管理员修改或 OAuth 刷新；完成后只统计剩余数量，不输出秘密。
- 先让所有会读写凭据的 API/Gateway/后台进程部署兼容读取，再启用密文写入；不能让只懂明文的旧进程读取新密文。简单部署可用维护窗口协调升级，不必新增长期双协议。已经写入密文后不能直接回滚到旧二进制，回滚需使用同样支持密文读取的版本或恢复匹配的备份。
- 原会话、消息、附件、压缩事件不属于凭据加密迁移范围，通常无需改写。继续旧会话时仍按当前 Provider ID 解析凭据，统一读取层负责兼容；若旧消息正文曾泄露秘密，那属于另一个历史数据治理问题，本课题不声称自动处理。

## 密钥如何部署：先给方向，待开发共同确认

建议首版每个独立部署环境一套随机生成的对称加密密钥，使用成熟认证加密库；API 和 Gateway 取得同一密钥材料。相比照搬 Dify 每租户 RSA 私钥体系，这更贴近当前 DeepAgent 的部署粒度。若平台要求租户级隔离或已有 KMS，则按平台方案调整，不在本次锁死算法与库。

1. **只初始化一次，持久保存。** 由部署流程生成或由平台 Secret 管理系统提供，通过挂载 Secret 文件或既有安全配置机制注入；不以数据库密码、项目名或固定常量派生，不在每次容器启动时重新生成。变量/文件名称尚未定稿。
2. **缺钥不自动补钥。** 发现已有密文却没有对应密钥时启动检查或相关操作应明确失败，不能创建新密钥假装恢复。密钥丢失一般意味着原密文不可恢复，只能恢复密钥备份或重配凭据。
3. **数据库与密钥配套恢复、分开保管。** 物理数据库备份只含密文并不够恢复；同环境升级必须保留密钥。跨环境迁移选择重新授权/填凭据，或由受控迁移程序解密再用目标环境密钥重加密，不直接假定密文跨环境可用。
4. **轮换保留旧 key_id。** 新写入切到新密钥，旧密钥只读解密；后台将旧密文重加密，核对存量和备份保留期后再停用旧密钥。密钥材料不写入日志或报表。
5. **与 Java 项目对齐待确认。** 后续核对现有平台是否提供统一 Secret/KMS、部署注入和轮换能力；本次未审计 Java 实现，不声称已有可复用组件。优先复用合适的部署机制，不直接复用未知来源的固定加密密钥。

## 增补验收

旧明文能继续调用且查询不泄露；旧配置只改名称再保存会转换；新配置始终密文；OAuth 刷新后仍密文；批量迁移中断可重跑；并发修改不丢失；篡改、未知版本和缺钥不能退回明文；旧备份恢复与轮换后的旧密钥读取可验证；历史会话重开及继续调用不受影响。实施发布前确定全部凭据消费者已升级。
