# 通用渠道工具：源码对照与设计草案

> 2026-09-27。用户确认方向：撤回飞书专用媒体工具；按网关式适配设计通用渠道能力，可先只实现飞书。本文是设计草案，不代表新工具已经实现。上游依据当日官方 main/master 源码，不等同于用户本机安装版本。

后端定向回归 140 项、渠道前端 31 项通过；重启本地 API 与 Gateway，确认旧路由和系统工具目录消失、飞书与两个企微账号重新连接。该撤回与扫码、帮助界面调整一起纳入 v0.11.9；新工具尚未实现。

## 两家的抽象

| 主题 | OpenClaw | AstrBot |
| --- | --- | --- |
| 发送入口 | message 的 send 动作，渠道插件实现标准动作适配 | send_message_to_user 接收有序组件，组合 MessageChain 后按统一会话标识交给平台 |
| 消息操作 | 公共动作还涵盖读取、编辑、删除、表情、置顶、搜索等；按渠道支持范围暴露 | 本次核验的内置发送工具主要负责发送组件；未找到同等覆盖面的统一消息动作入口 |
| 外部会话 | conversations_list/send/turn 提供发现、直接发送及关联回复等待；与本地 sessions 工具区分 | 发送可指定统一目标会话，跨会话有管理员权限检查；不是任意联系人发现能力 |
| 历史 | message read/search 依平台适配；本地 sessions_history 是另一类数据 | 独立 get_group_message_history 查询本机持久化的当前群消息，受配置开关约束 |
| 调度 | 调度触发与渠道投递分层 | future_task 提供任务管理，投递复用消息能力 |
| 平台专属业务 | 飞书日历、文档、多维表格等作为专用工具/插件 | 平台专用能力可通过插件扩展；不视为所有渠道通用承诺 |

OpenClaw 飞书官方插件本次核验实际声明 send/react/reactions/delete/unsend，不能将核心 message 动作全集当作飞书全支持。统一接口允许各平台能力不对等。

## 建议职责与调用链

Agent 工具 / 后台任务 → 统一渠道操作服务 → 网关适配器注册表 → 目标渠道适配器 → 官方 SDK。

- 统一契约置于现有 channels/contracts 与 registry 边界；上层依赖协议，不按 feishu 硬编码装配。保留现有入站、排队、流式回复生命周期。
- 工具层负责模型参数与结果呈现；操作服务负责授权、目标解析、文件取用与发送记录；Gateway 负责连接和分发；适配器负责平台 ID、媒体上传、SDK 错误与消息格式。
- 每个适配器声明动作、内容类型、大小限制、引用/线程/主动发送支持。没有实现的能力返回明确不支持，不能悄悄用文本链接冒充媒体发送成功。
- 模型实际可见能力取适配器实现、账号配置与运行授权的交集；平台权限未知时不伪称已授权，执行时据官方结果区分权限错误。
- 普通正文仍经现有流式回复路径；额外消息/图片/文件走显式发送，避免两条路径重复投递。暂不统一各平台流式动画与卡片实现。

## 统一数据语义

以下为建议结构，字段名尚未锁定：

| 对象 | 职责 |
| --- | --- |
| 渠道运行上下文 | 服务端持有账号、执行主体、来源聊天/消息/线程与授权目标范围；来自可信入口，正文不可伪造 |
| 目标引用 | 账号范围内的用户、群聊或话题；与 DeepAgent session_id、平台业务用户身份分开 |
| 消息内容 | 有序文字、图片、文件组件；媒体引用复用已授权 file_id，不要求模型处理 image_key/file_key |
| 操作 | send 为首个实现；其他动作按实际适配能力逐项加入，不使用任意 URL/任意 SDK 方法透传 |
| 回执 | 返回每条实际消息的 ID 和结果；一组内容可能被拆成多条消息，允许部分成功及结果未知 |

当前会话发送可默认继承来源；跨会话/主动发送须有显式授权目标。新接口不能依赖“当前必须有正在回复的入站 MessageJob”，否则定时、轮询、其他触发源仍无法复用。是否向普通控制台运行开放，由授权上下文决定，不因已有渠道账号而全局开放。

发送服务负责幂等和失败语义。重试同一次投递不能再次发送；上传成功不等于投递成功；超时不等于拒绝。若开放脱离 Run 的主动投递，需确定持久化投递回执及重启恢复规则，不能沿用仅存在活动任务中的去重字典。

## 工具边界与实施顺序建议

1. 首先定义统一消息操作契约及能力声明；实现通用发送入口和飞书适配，覆盖文字、图片、文件、引用、当前会话和受授权目标。名字可用 channel_message，展示“渠道消息”；最终协议名称待实现评审，不保留旧工具别名。
2. 目标发现/解析与历史读取按需求独立设计。目录支持只是候选来源，不赋予向所有联系人发送的权限。平台历史、本地已接收渠道记录、Agent 模型历史必须明确来源。
3. 表情、撤回、编辑、置顶等归消息动作，按渠道声明；不为每个渠道复制整套工具。
4. 定时与轮询是触发源，复用同一个投递服务，不各建一套发送接口。调度工具不归渠道适配器所有。
5. 文档、日历等平台独有业务保留专用插件，不把所有 API 包成万能“渠道工具”。

第一阶段只实现飞书可以检验真实闭环，但还需用无飞书字段的测试适配器验证契约独立性。现有企微收发流程不为验证抽象而改造；以后扩展企微时单独适配和验收。
